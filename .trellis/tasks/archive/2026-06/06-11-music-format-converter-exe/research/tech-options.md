# 音乐格式转换工具技术调研

## 目标理解

用户目标是做一个“任意格式音乐转任意格式”的程序，最终导出可迁移的 Windows `exe`。
当前仓库基本为空，适合从零搭建，但也意味着需要先收紧 MVP 范围，否则“任意格式”会变成不可验证的承诺。

## 结论摘要

### 推荐核心引擎：FFmpeg

优先推荐 `FFmpeg` 作为实际转码引擎，而不是自己实现解码/编码流程。
原因：

- 支持格式和编解码器范围远大于常规 Python 音频库
- 社区成熟，文档完善，长期可维护
- 适合做批量转换、参数透传、元数据处理
- 最终程序只需要封装调用，不需要自己实现音频编解码

### 不推荐自己手搓转码能力

自己实现“任意格式互转”本质上会落到：

- 自己处理不同容器和编解码器
- 自己处理采样率、声道、比特率、元数据
- 自己处理错误文件、损坏文件、兼容性差异

这个方向成本极高，且不符合“优先使用开源库”的要求。

## 方案对比

### 方案 A：Python + FFmpeg CLI + 简单桌面 GUI（推荐）

结构：

- Python 负责界面、任务编排、参数校验、日志、错误展示
- `ffmpeg.exe` / `ffprobe.exe` 负责探测与转码
- 用 `PyInstaller` 打包成 Windows `exe`

优点：

- 实现最直接
- 依赖少，适合空仓快速落地
- 便于做单文件或单目录打包
- 对 FFmpeg 能力保留最完整，不会被上层封装限制

缺点：

- UI 原生感一般
- 需要处理打包时外部二进制随程序分发的问题

适用结论：

- 最适合作为首版 MVP

### 方案 B：Python + `pydub` + FFmpeg

结构：

- 用 `pydub` 做高层音频读写
- 实际底层仍依赖 `ffmpeg` 或 `libav`

调研结论：

- `pydub` 很适合简单音频切片、拼接、淡入淡出
- 非 wav 格式仍依赖 `ffmpeg`
- 对“任意格式互转”这种工具型需求，抽象层反而可能限制参数控制

优点：

- API 简单
- 适合做音频编辑类增强功能

缺点：

- 本质仍绕不开 FFmpeg
- 对高级转码参数、元数据和异常处理不如直接调用 FFmpeg 清晰

适用结论：

- 可作为辅助库，但不建议作为核心转码抽象

### 方案 C：Python + `ffmpeg-python` + FFmpeg

结构：

- 用 `ffmpeg-python` 生成 FFmpeg 命令
- 底层仍调用系统或打包的 `ffmpeg`

调研结论：

- `ffmpeg-python` 只是 Python 封装，不负责安装 FFmpeg
- 适合复杂 filter graph 的程序化构建
- 对“文件转文件”的常规转换器来说，直接拼命令行通常更简单、更可搜索

优点：

- 对复杂流水线更优雅
- 适合需要程序化拼接大量 filter 的场景

缺点：

- 增加一层抽象
- 对当前 MVP 不一定比 `subprocess` 更简单

适用结论：

- 若后续要做复杂滤镜链可考虑
- 首版不如直接调用 `ffmpeg` 简洁

### 方案 D：Tauri / Electron 桌面端 + FFmpeg

优点：

- UI 可做得更现代
- 易扩展拖拽、任务列表、主题等

缺点：

- Tauri 需要 Rust 工具链
- 工程复杂度明显高于 Python 首版
- 当前仓库为空，不利于快速验证核心能力

适用结论：

- 适合未来升级，不适合作为首版最低成本方案

## 打包调研

### 推荐打包路线：先单目录，再单文件

`PyInstaller` 调研结果：

- 可打成 one-folder 或 one-file
- one-file 启动时会先解包到临时目录，启动略慢
- one-folder 更利于调试依赖问题
- 打包产物和操作系统、Python 版本、位数相关，Windows 版 `exe` 需要在 Windows 环境构建

建议：

1. 开发期先做 `one-folder`
2. 稳定后再产出 `one-file exe`
3. 若“可迁移”要求极强，需要同时验证目标机器是否缺少 VC 运行库等系统依赖

## 关于“可迁移 exe”的现实边界

“一个 exe 到处跑”可以追求，但不能无条件承诺：

- 不同 Windows 版本兼容性需要验证
- 首次启动可能受杀软、系统权限、临时目录策略影响
- 单文件打包不等于完全无外部依赖
- 若内置 `ffmpeg.exe`，仍需要妥善处理资源提取与调用路径

更稳妥的表述应是：

- 首版目标为“Windows 可分发、普通用户双击可用的便携版 exe”
- 再通过测试逐步提升兼容性声明

## 许可与合规风险

### FFmpeg 许可

FFmpeg 官方文档说明：

- FFmpeg 主体是 `LGPL v2.1+`
- 若启用某些可选组件，会整体落到 `GPL`
- 官方明确强调分发时需要做合规处理

对本项目的影响：

- 如果最终程序内置并分发 FFmpeg 二进制，必须考虑许可证文本、来源说明、可能的源码对应关系
- 若使用带 GPL 组件的构建包，项目整体分发策略要更谨慎
- 还存在编解码专利风险，尤其商业分发时更要注意

工程建议：

- 首版尽量使用来源清晰的 FFmpeg 构建
- 文档中显式保留第三方依赖说明
- 在产品承诺里避免“完全无版权风险”之类表述

## 首版 MVP 建议范围

推荐先支持常见音频格式互转：

- 输入：`mp3` `wav` `flac` `m4a` `aac` `ogg` `opus` `wma`
- 输出：`mp3` `wav` `flac` `m4a` `aac` `ogg` `opus`

推荐首版功能：

- 单文件转换
- 批量转换
- 选择输出格式
- 选择输出目录
- 基础参数：比特率、采样率、声道
- 保留基础元数据（能保留则保留）
- 显示转换进度与失败原因
- 导出 Windows `exe`

首版暂不承诺：

- DRM 文件
- 极冷门或私有格式
- 所有损坏文件都能处理
- 完整无损保留全部元数据/封面
- 跨平台安装包

## 推荐技术决策

### MVP 推荐栈

- 语言：Python 3.x
- GUI：`tkinter` 或 `customtkinter`
- 转码引擎：`FFmpeg`
- 探测：`ffprobe`
- 打包：`PyInstaller`

### 推荐实现方式

- 不把 `pydub` 作为核心转码层
- 不把 `ffmpeg-python` 作为必需依赖
- 直接由 Python 通过 `subprocess` 调用 `ffmpeg` / `ffprobe`

原因：

- 更简单
- 更容易定位问题
- 命令参数与官方文档直接对应
- 更适合空仓最小实现

## 下一步待确认问题

当前最关键的范围问题：

1. “任意格式音乐”是否只指音频文件，不包含从视频里提取音频
2. 首版是否接受“常见格式集合”而不是绝对意义上的“任意格式”
3. 是否只先做 Windows 便携版 `exe`
